2 GPU rendering

How long each frame takes to draw. Over 16.7 ms means a dropped frame at 60 FPS.

What this tells us

When the app is quiet the frames stay under budget, so the UI is fine at rest. The problem is the response views: in S2 the raster time averaged 25.5 ms and 34% of frames were janky; with the big JSON (S3) raster averaged 38.5 ms and 59% of frames were over budget.

The worst frame had a build of 281 ms, which is the moment the big JSON is parsed. Almost all the cost is in the raster phase, not in building widgets, which fits the fact that the app has no explicit RepaintBoundary widgets.

Source: DevTools Performance export · 125 + 231 frames · 60 Hz.

3 Overdraw (repaints)

How many times each part of the screen is repainted. Fewer is better.

What this tells us

During this recording the average dropped to 17 FPS and 89% of frames were janky. The repaint counts show the cost is in a deep tree of layout boxes (ConstrainedBox, Padding, PositionedBox, Flex), the semantics tree, and the highlighted text (RenderParagraph).

There are only ~770 RepaintBoundary compared to thousands of repainted boxes, so large parts of the screen repaint together. Adding a RepaintBoundary around the response and preview area would help.

Source: DevTools trace with paint profiling · same three views.

4 Memory

What holds the Dart heap, and whether memory is leaking.

What this tells us

No leak: the app's own objects are single instances (1 CollectionStateNotifier, 1 HttpClientManager, 1 RequestModel). All apidash classes together are only ~1.2 KB.

About 92% of the heap is the Lottie animation of the sending widget (14,473 objects). It is reused, not leaked, but it is the heaviest thing in memory and the same widget that adds raster cost in Figure 1.

Source: DevTools heap snapshot · class list export.

Reading it

The ten biggest classes are all from Lottie (Keyframe, CubicCurveData, the keyframe animations). This is expected for a vector animation: it keeps the curves and keyframes in memory while it plays.

Most of this sits in old space, which means the GC already promoted these long-lived objects. RAM stayed flat around 400–500 MB across S1–S5, so the app does not accumulate memory as it runs.

5 Threading

What the CPU does on the main isolate while loading a big response.

What this tells us

The app runs on a single main isolate. While loading the big response, the CPU spends its time building lists and copying bytes (parsing the JSON), laying out text, and doing CRC32 for decompression. All of this runs on the main isolate, right next to the frame drawing.

That is why the big response gives the 281 ms spike in Figure 1. The network wait itself does not use CPU and does not block the UI, so the async design works; the bottleneck is the parsing that stays on the main thread. Moving it to a compute()/isolate would help the most.

Source: DevTools CPU Profiler export · 694 samples over 409 ms.

6 Summary

Good

  • The network wait never blocks the UI — all calls are async.
  • Memory is steady (400–500 MB), no leaks, thanks to const, immutable models and lazy Hive boxes.
  • Timers, controllers and stream subscriptions are all released in dispose().

Problems

  • Parsing a big response runs on the main isolate, causing jank on large bodies (S3).
  • No explicit RepaintBoundary, so deep trees and text repaint together.
  • leak_tracker is not set up in the tests.
